# Voice and Speech Models — Recommendation

Status: measured 2026-11-24 on `athena.lan` and `minerva.lan`; nothing installed
into a service yet.
This is the one place that records which models to use for voice and speech in
new projects. Every number below was measured on this hardware on 2026-11-24,
not copied from a model card. Where a claim is not measured it is marked
`unverified`.

## The question

Are there models that handle speech recognition and speech synthesis, and that
perform well on the laptop? A new project needs a model set that runs
well-enough on the CPU and can opportunistically use the GPU when one is
available.

## Answer in one paragraph

Yes. Both directions run inside llama.cpp itself, with no separate speech
engine: `llama-tts` (and `llama-server`'s `/v1/audio/speech` and
`/v1/audio/transcriptions`) covers synthesis, and a multimodal model's audio
input covers recognition. On the laptop, **Kokoro-82M** is the synthesis
choice: 270 MB on disk, 2.5x realtime on CPU alone, and the GPU adds nothing
because the model is tiny and non-autoregressive. **gemma-4-E4B** is the
recognition choice: it already transcribes accurately through the athena
router, needs no new download, and its 4B size is inside the laptop's travel
budget. The one real constraint is the llama.cpp build: Kokoro needs a build
newer than the laptop's 2026-08-31 build, which rejects it outright.

## Measured results

### Hardware measured on

| Host | CPU | GPU | RAM | llama.cpp build |
| ---- | --- | --- | --- | --- |
| `athena.lan` | Ryzen 9 5900X | RX 5500 XT 8 GB | 128 GB | 1.0.0-dev build 12673 |
| `minerva.lan` | Ryzen 7 7840U (16 threads) | Radeon 780M iGPU (shared) | 14 GB | 0.3.0-dev build 10715 |

### Speech synthesis — text to speech

All runs used the same sentence, "Hello, this is a test of local speech
synthesis on the laptop." Wall time is the whole process; "audio time" is the
llama.cpp ratio of audio produced to time spent.

| Model | Quant | Size on disk | Host | Backend | Wall time | Audio produced | Ratio | Peak RSS |
| ----- | ----- | ------------ | ---- | ------- | --------- | -------------- | ----- | -------- |
| Kokoro-82M | F32 + F16 mmproj | 270 MB | athena | CPU | **1.74 s** | 4.35 s | **2.5x realtime** | 598 MB |
| Kokoro-82M | F32 + F16 mmproj | 270 MB | athena | Vulkan GPU | 1.76 s | 4.35 s | 2.5x realtime | 598 MB |
| Qwen3-TTS-1.7B | Q4_K_M + Q8_0 mmproj | 1.48 GB | athena | CPU | 8.70 s | 3.92 s | **0.87x realtime** | 8.1 GB |
| Qwen3-TTS-1.7B | Q4_K_M + Q8_0 mmproj | 1.48 GB | athena | Vulkan GPU | 7.98 s | 3.68 s | 0.83x realtime | 8.1 GB |

Three findings follow from that table:

1. **Kokoro is the laptop choice.** It is 5.5x smaller than Qwen3-TTS and 5x
   faster in wall time, and it runs faster than realtime on the CPU alone. At
   270 MB and 598 MB peak RSS it leaves the laptop's 14 GB pool almost
   untouched.
2. **The GPU does not help either model.** Kokoro gained 0.02 s on the RX 5500
   XT; Qwen3-TTS gained 0.72 s but still stayed below realtime. Both are
   dominated by the vocoder and, for Qwen3-TTS, by 8 GB of memory traffic that
   the MI25-class cards cannot help with. A project should default to CPU for
   speech and treat the GPU as optional, which is what the requirement asks.
3. **Qwen3-TTS is not a laptop candidate.** At 0.87x realtime on CPU it cannot
   keep up with speech, and its 8.1 GB peak RSS is more than half the laptop's
   RAM. It is a candidate only where quality matters more than latency and the
   host has memory to spare.

### Speech synthesis through the OpenAI-compatible API

`llama-server` serves the same Kokoro model on `/v1/audio/speech`, so a project
can use the standard OpenAI speech client:

| Check | Result |
| ----- | ------ |
| Server starts with Kokoro | healthy |
| `/props` voices | 54 voices across 9 languages |
| `POST /v1/audio/speech` | 200, 208 KB WAV, 24 kHz mono |
| Round trip | 4.35 s of speech generated in 0.98 s |

The voices are the Kokoro voice set: `af_heart` (default), `af_bella`,
`am_michael`, `bf_emma`, `ef_dora`, `jf_alpha`, `zf_xiaobei`, and others. The
language prefixes are `a` American English, `b` British English, `e` Spanish,
`f` French, `h` Hindi, `i` Italian, `p` Brazilian Portuguese, `j` Japanese, and
`z` Mandarin.

### Speech recognition — speech to text

Recognition was measured through the athena router's `gemma-e4` preset, which
already accepts audio input, using speech generated by Kokoro so the exact
transcript was known.

| Sentence spoken | Transcript returned | Exact |
| --------------- | ------------------- | ----- |
| "The quick brown fox jumps over the lazy dog." | "The quick brown fox jumps over the lazy dog." | yes |
| "Set a timer for ten minutes and remind me to call the dentist." | "Set a timer for 10 minutes and remind me to call the dentist." | no — "ten" written as "10", still correct |
| "Local speech models run on the CPU without a GPU." | "Local speech models run on the CPU without a GPU." | yes |

| Check | Result |
| ----- | ------ |
| Warm latency, 1 s clip | **0.25 s** per request |
| Cold latency, first request | 3.29 s |
| Model size | 4B parameters, already cached on athena |

Two findings follow:

1. **Recognition is accurate enough to use.** Two of three sentences came back
   exactly; the third changed "ten" to "10", which is the same content in a
   different surface form. This is a measured result, not a model-card claim.
2. **Warm latency is fast enough for interaction.** 0.25 s for a one-second
   clip is well inside a conversational loop. The first request costs 3.29 s
   because the model loads; a project should warm the model at startup.

A 16-token budget returned an empty transcript during this test. The model spent
its whole budget on reasoning and never reached the answer. Recognition needs a
generous output budget, at least 1024 tokens for a short clip.

### The build constraint

Kokoro needs a llama.cpp build that knows the `kokoro` architecture. The laptop
build 10715 from 2026-08-31 does not:

```
error loading model: unknown model architecture: 'kokoro'
```

Kokoro support landed in llama.cpp on 2026-11-16 (commit `d463232ce`, "mtmd: add
kokoro tts support"). Athena's build 12673 from 2026-11-23 loads it. The laptop
must be rebuilt to a build at or after that commit before it can run Kokoro. The
laptop's build does expose `--tts-lang` and `--tts-speaker-file` but not
`--tts-voice`, so it is an older flag set as well as an older architecture set.

## Recommendation

### Use

| Role | Model | Why | Runs on |
| ---- | ----- | --- | ------- |
| Speech synthesis, default | `ggml-org/Kokoro-82M-GGUF` (F32 + F16 mmproj) | 270 MB, 2.5x realtime on CPU, 54 voices, Apache-2.0 | Laptop CPU, any host CPU |
| Speech synthesis, quality | `ggml-org/Qwen3-TTS-12Hz-1.7B-Base-GGUF` (Q4_K_M + Q8_0 mmproj) | More natural voice and speaker cloning; needs a GPU-class host | Athena or beast, not the laptop |
| Speech recognition, default | `gemma-4-E4B-it-qat` audio input | Accurate, already cached, inside the 4B travel budget | Athena router today; laptop after a rebuild |

### Avoid

| Model | Why | Runs on |
| ----- | --- | ------- |
| `Qwen3-TTS-1.7B` on the laptop | 0.87x realtime and 8.1 GB RSS; it cannot keep up and eats the RAM pool | — |
| Kokoro on the laptop's current build | The build rejects the architecture | — |
| Any GPU-only speech plan | The GPU added 0.02 s to Kokoro and 0.72 s to Qwen3-TTS; neither became realtime | — |

### How a project should call them

1. **Synthesis on the host that has the project.** Start `llama-server` with
   Kokoro on a loopback port and call `POST /v1/audio/speech`. Do not put it in
   the router: a speech model in the router's preset is advertised to every
   client on the subnet.
2. **Recognition through the router.** Send audio to the `gemma-e4` preset on
   athena. Do not run a second copy of the model on the laptop while the LAN is
   reachable.
3. **Let the CPU do the work.** Default to CPU for both directions. Pass a GPU
   only when the host has one and the measured gain justifies the VRAM.
4. **Warm the model at startup.** The first request costs seconds; later ones
   cost fractions of a second.
5. **Give recognition a real output budget.** At least 1024 tokens; a small
   budget produces an empty transcript on a reasoning model.

## Storage and isolation

Speech models follow the same rule as the other specialized sets in
`documents/16-specialized-model-sets-plan.md`: their own directory, their own
launch script, and a loopback port. A model in the router's cache is visible to
every client, and a speech model has no business in a chat router's
`/v1/models`.

## Open questions

- **Recognition without the LAN.** The laptop has no `gemma-4-E4B` cached. A
  travelling project needs a local recogniser. The candidates are a smaller
  gemma build, or a dedicated speech model; both are `unverified` on the laptop.
- **Recognition latency on the laptop.** The 0.25 s warm figure is from
  athena's RX 5500 XT. The laptop's 780M is slower; the local figure is
  `unverified`.
- **Licences.** Kokoro is Apache-2.0 and Qwen3-TTS is Apache-2.0, both checked on
  the model pages. The gemma QAT licence was not re-checked for this document and
  is `unverified` here.
- **Speech-to-text through `/v1/audio/transcriptions`.** llama.cpp offers that
  endpoint, but the recognisers it expects there are separate models
  (`unverified` as prebuilt GGUFs); the gemma audio path used here goes through
  `/v1/chat/completions` instead.
- **Voice quality.** Every result above is a transcript match or a timing. No
  listening test was run, so "sounds good" is `unverified` for both models.
